# microcontrollers

AVR assembly/C labs (ATmega328PB) for a "Microcontrollers" university course
(Greek: Εργαστήριο Μικροϋπολογιστών), targeted at a physical **ATmega328PB
Xplained Mini** dev board.

## Layout

One folder per exercise, named `exN-<topic>` (`ex1-intro`, `ex2-interrupts`,
`ex3-adc-pwm`, `ex4-adc-lcd`, `ex5-i2c`, `ex6-keypad`, `ex7-temp-sensor`,
`ex8-final-project`), one subfolder per **standalone program** inside it (a
numbered sub-exercise like `1.1`, `2.2`, or `2.3_asm`/`2.3_C` where both an
assembly and a C version exist). Each sub-exercise folder is an independent
project: it has its own `main.asm` or `main.c`, its own `Makefile`, and its
own `.vscode/tasks.json` — two interfaces to the exact same build/flash
commands, use whichever's convenient. Inside each exercise folder,
`exN-instructions.pdf` is the professor's assignment sheet and `Report.pdf`
is the lab report covering all of that exercise's sub-parts (gitignored —
see below).

To work on one: open that specific subfolder in VS Code (`File > Open
Folder`), not the repo root — VS Code only reads `.vscode/tasks.json` from
the currently-opened folder, so tasks won't show up if you have the whole
`microcontrollers/` tree open instead.

**Known exception:** `ex7-temp-sensor/7.1/main.c` has no `main()` — it's a
one-wire helper-function fragment (superseded by the complete, independent
implementation in `7.2`), not a flashable program. Its build task will fail
on `undefined reference to 'main'`; that's expected, not a bug in the setup.

## The toolchain gotcha (read this first)

This started life as an MPLAB X project built with **XC8 v3.10**. XC8 v3.10
dropped the legacy `avrasm2` assembler for AVR entirely — its `.asm` build
step is actually **GNU `as`** (via `xc8-cc.exe`), incompatible with the
**Atmel/Microchip Studio `avrasm2` dialect** (`.equ NAME=value`, `.include
"m328PBdef.inc"`) all the `.asm` files here are written in. Building them
through XC8 3.10 fails with errors like:

```
can't open m328PBdef.inc for reading: No such file or directory
expected comma after "FOSC_MHZ"
```

The professor's instructions call for `avrasm2` specifically, and it's
still installed as part of the **XC8 v2.10** package:

- Assembler: `C:\Program Files (x86)\Microchip\xc8\v2.10\avr\bin\avrasm2.exe`
- Device include: `C:\Program Files (x86)\Microchip\xc8\v2.10\dfp\avrasm\inc\m328PBdef.inc`

The `.c` files, by contrast, build fine on XC8 v3.10 (`xc8-cc.exe`) — that's
its native language, no workaround needed there.

Rather than fight MPLAB's generated CMake/ninja build graph (which is wired
for the GNU-flag-compatible XC8 v3.10 pipeline, is regenerated by the IDE on
its own schedule, and doesn't scale to 23 hand-maintained projects anyway),
every project here bypasses it with plain **VS Code tasks and a Makefile**
that call `avrasm2`, `xc8-cc`, and `avr-objcopy` directly. This is the
low-risk approach — it doesn't touch anything MPLAB owns/regenerates, and
each project folder is fully self-contained (both interfaces read paths
relative to that folder, nothing repo-wide to keep in sync).

## Building

`Ctrl+Shift+B` inside a project folder runs its default build task, which
writes into that project's own `out/`.

**Assembly projects** (`main.asm`) — one task, `avrasm2`:

```
"C:\Program Files (x86)\Microchip\xc8\v2.10\avr\bin\avrasm2.exe" -fI ^
  -o "out\main.hex" -l "out\main.lst" -m "out\main.map" ^
  -I "C:\Program Files (x86)\Microchip\xc8\v2.10\dfp\avrasm\inc" ^
  "main.asm"
```

Success looks like `Assembly complete, 0 errors. 0 warnings`.

**C projects** (`main.c`) — two chained tasks, `xc8-cc` then `avr-objcopy`:

```
"C:\Program Files\Microchip\xc8\v3.10\bin\xc8-cc.exe" ^
  -mcpu=ATmega328PB -x c ^
  -mdfp="C:\Users\sgkio\.mchp_packs\Microchip\ATmega_DFP\3.6.299\xc8" ^
  -O1 -ffunction-sections -fdata-sections -fshort-enums -funsigned-char ^
  -funsigned-bitfields -Wall -Wno-error -gdwarf-3 -mno-const-data-in-progmem ^
  "main.c" -o "out\main.elf"

"C:\Program Files\Microchip\xc8\v3.10\bin\avr-objcopy.exe" -O ihex "out\main.elf" "out\main.hex"
```

Two flags worth knowing if you change these by hand:
- `-O1`, not MPLAB's usual `-O0` — at `-O0`, `<util/delay.h>`'s
  `_delay_ms`/`_delay_us` calls don't actually produce the requested delay
  (the compiler warns about this explicitly). Several exercises rely on
  these, so `-O1` is required for correct timing, not just style.
- `-Wno-error` — this XC8 build treats certain old-style-C warnings
  (implicit function declarations, signedness mismatches) as hard errors by
  default. The lab source predates that default; `-Wno-error` downgrades
  them back to warnings without changing any source file. Three exercises
  (`4.2`, `4.3`, `6.2`) fail to build without it.

All 22 real programs (everything except the `7.1` fragment noted above)
were verified to build clean with this exact setup.

## Command line: `make`

Every project also has a `Makefile` that runs the exact same commands as
its `.vscode/tasks.json` (`make` = build task, `make load` = build then
flash, `make clean` = remove `out/`'s contents). Use whichever interface is
convenient — they're kept equivalent, not two different setups.

**One-time setup:** `make` needs to be on PATH. It's installed via winget:

```
winget install ezwinports.make
```

This is the actively-maintained native-Windows GNU Make port (not the
abandoned 2006-era `GnuWin32.Make` winget also lists) — same 4.4.1 build
MPLAB X itself bundles internally, just properly registered on PATH this
time. Winget adds it to your user PATH automatically as part of the
install; restart any open terminal/VS Code window afterward for that to
take effect. Confirm with `make --version`.

(The Makefiles' own tool paths — `avrasm2`, `xc8-cc`, `avrdude`, `rm`, etc. —
are all absolute, so nothing else needs to be on PATH.)

Every project's `Makefile` pins `SHELL` to `cmd.exe` explicitly, so `make`
behaves identically whether you run it from PowerShell, cmd, or Git Bash —
it doesn't depend on which shell launched it.

## Flashing the board

The board is an **ATmega328PB Xplained Mini** — it has an onboard debugger
(mini-EDBG chip) built in, so a single USB cable is all you need; no
separate programmer.

Run `make load`, or the VS Code task **"avrdude: flash to ATmega328PB
Xplained Mini"** — either rebuilds first automatically, then runs
(equivalent command line, from inside a project folder):

```
avrdude -c xplainedmini_isp -p m328pb -U flash:w:out\main.hex:i
```

`avrdude` (installed via `winget install AVRDudes.AVRDUDE` — a native
binary with no PATH entry needed since the Makefiles/tasks call it by
absolute path) talks to the same onboard mEDBG debugger MPLAB IPE does,
just without MPLAB IPE's several-seconds-per-invocation JVM/tool-pack
startup: a full `make load` (build + flash + verify) runs in well under
5 seconds, versus 20-30s through `ipecmd`. `xplainedmini_isp` is the
programmer type for this exact board (the Xplained Mini's onboard debugger
in ISP mode); `m328pb` is avrdude's part name for the ATmega328PB.

Success ends with `avrdude done. Thank you.` after a "bytes of flash
verified" line, exit code 0.

If flashing reports it can't find the programmer/device, reconnect the USB
cable and retry — Windows sometimes enumerates the board's composite USB
interfaces (a COM port + an HID device) before the Microchip tool layer has
attached to them.

## Slower alternatives (MPLAB IPE / ipecmd)

`ipecmd.exe` (bundled with MPLAB X — no separate install) does the same
job, just much slower per invocation (JVM + tool-pack startup each time):

```
"C:\Program Files\Microchip\MPLABX\v6.35\mplab_platform\mplab_ipe\ipecmd.exe" ^
  -PATmega328PB -TPMEDBG -F"out\main.hex" -M -YP
```

Key gotcha if you ever do use it: the board's onboard debugger identifies
to `ipecmd` as **`MEDBG`** (`-TPMEDBG`), *not* `EDBG` — that's specific to
the Xplained Mini's mini-EDBG chip. Other tool IDs (`EDBG`, `NEDBG`,
`PKOB4`, ...) come back "Programmer not found." Success ends with `Program
Succeeded` / `Verify Succeeded` / `Operation Succeeded`. Its `-YP` verifies
program memory only — a full verify (`-Y` with no region) reports a
mismatch in configuration/fuse memory, which is expected and harmless:
none of these `.hex` files touch fuses, so a full verify compares fuses
against nothing.

MPLAB IPE (`C:\Program Files\Microchip\MPLABX\v6.35\mplab_platform\bin\mplab_ipe64.exe`)
is the GUI version of the same tool: pick Device `ATmega328PB`, Tool =
whatever shows in the dropdown once the board is plugged in (the MEDBG
entry), browse to a project's `out\main.hex`, click Program.

## Adding a new exercise / sub-project

Copy an existing project folder of the matching language (any `.asm` one
for assembly, any `.c` one for C) as a template — neither its
`.vscode/tasks.json` nor its `Makefile` need changes, since every path in
both is relative to the project folder itself. Just drop in the new
`main.asm`/`main.c` and either open that folder in VS Code or run `make`
from inside it.

## `lib/` — shared board driver library

`lib/ntuaboard.h` + `lib/ntuaboard.c` consolidate the C driver functions
that recur across Ex5–Ex8 (TWI, the PCA9555 expander, the keypad, the LCD,
the DS18B20, USART/ESP) plus an ADC and Timer1-PWM layer that wasn't
handed out as named functions anywhere but every exercise sets up the same
way by hand — all under the same function names those exercises already
use, so it's a drop-in for new C projects rather than another dialect to
learn. It compiles clean with `-Wall -Wextra` and was link-tested against
a program that calls every function in it.

It isn't wired into any existing project's build (each project's
`Makefile`/`tasks.json` still only points at that project's own
`main.c`/`main.asm`) — to use it in a new project, add `lib/ntuaboard.c`
as a second source file to compile and `-I` the `lib/` directory, then
`#include "ntuaboard.h"`.

One deliberate difference from the Ex8 original: `usart_receive_str` here
takes a caller-supplied buffer and returns it, rather than the original's
no-argument version that returned a pointer to its own local stack array
— undefined behavior the moment the function returns. `usart_command`'s
signature changed to match.

`lib/examples/` has every C exercise that actually touches one of these
peripherals, rewritten to use this library instead of its own copy of the
driver code — see `lib/examples/README.md` for the full list and
`make EX=<name>` / `make EX=<name> load` to build/flash one.
